# 릴레이 실험 설계 (2026-10-04)

## 왜 릴레이인가
MOQ의 핵심은 **릴레이를 거치는 발행·구독**이고, 릴레이는 페이로드를 열지 않고 MOQT 헤더(트랙, 그룹·객체 ID,
우선순위, 전달 타임아웃)만 보고 전달·캐시·폐기한다. 지금까지(al-v1~v4)는 장치→수신자 직결이라
"QUIC 스트림 두 개면 되지 않나"에 답할 수 없다. 이 실험은 다음을 보인다.

> 검사 장치가 경보 우선 규칙을 **MOQT 헤더로만 표현**하면, 장치를 모르는 릴레이가 그 규칙을 지켜
> 요구가 다른 여러 구독자에게 동시에 경보 지연 예산을 보장하고, 끊겼던 구독자는 장치에 부담 없이
> 릴레이 캐시에서 빠진 경보를 FETCH로 복구한다.

기존 al-v3/v4 결과는 "첫 홉(장치→릴레이)"의 결과로 그대로 쓴다.

## 연구 질문
| | 질문 | MOQT 요소 (draft-21) |
|---|---|---|
| Q1 | 릴레이→구독자 링크가 혼잡할 때 릴레이가 경보 지연 예산을 지키는가, 그러려면 릴레이 송출 규칙이 무엇이어야 하는가 | 우선순위 §5.1.2, 서브그룹 스트림 §2, 전달 타임아웃 §5.2 |
| Q2 | 요구가 다른 구독자(경보만 / 경보+이미지 / 기록)를 장치 업링크 1회 발행으로 동시에 만족하는가 | 트랙 단위 구독, 팬아웃 |
| Q3 | 수 초~수십 초 끊긴 구독자, 늦게 들어온 구독자가 빠진 경보를 전부 복구하는가, 장치 업링크는 영향을 받는가 | FETCH(standalone/joining), 릴레이 캐시, PRIOR_GROUP_ID_GAP §10.8 |

## 토폴로지 (구현 확정, 10/4 새벽)
```
ESP32-S3 ──Wi-Fi──[첫 홉: 512 kbit/s, 5 ms, 손실·단절 없음]──► moq_relay (호스트, C)
                                                                 ├─ netns moqsub1 ctrl : 결과만         f128  (128k, 지터 5 ms, GE 손실, 단절)
                                                                 ├─ netns moqsub2 mon  : 결과+이미지     f128
                                                                 ├─ netns moqsub3 qa   : 결과+이미지     f512
                                                                 └─ netns moqsub4 arch : 결과+이미지     trace (256k, 측정 지연 재생)
```
- 첫 홉을 512k로 셰이핑하는 이유: 장치가 첫 홉에 맞춰 표현을 고른다. 빠른 Wi-Fi 그대로면 고화질(약 64 KB)을 보내고,
  페이로드를 읽지 않는 릴레이는 그것을 512k 구독자에게 그대로 보내야 해 E가 0에 가까웠다(relay-smoke-1).
  손실·단절을 넣지 않는 이유: 정책 차이를 둘째 홉에만 남기기 위해.
- 둘째 홉 링크는 al-v3과 같은 정의, 셰이핑 방향은 릴레이→구독자(데이터 방향). 단절 일정은 라운드 시드로 구독자마다 다르게,
  같은 라운드의 정책끼리는 같게. 단절 시각은 links.json에 단조 시계로 기록.
- 시계: 릴레이 로그와 구독자 로그 모두 CLOCK_MONOTONIC → 홉별 분해(첫 홉 = 생산→릴레이 도착, 둘째 홉 = 릴레이 도착→구독자 도착).

## 릴레이 구현 (완료)
- `relay/moq_relay` (C): `relay/relay.c`, `relay/quic.c`. QUIC은 공식 ngtcp2 v1.25.0 + OpenSSL 3.6 백엔드(펌웨어용 ngtcp2 사본은
  ESP 진단 해킹이 있어 호스트에 쓰지 않음). 하류 세션마다 펌웨어의 portable 코어(`moqt_core.c`, draft-21 코덱)를 그대로 사용 →
  SUBSCRIBE/FETCH/객체 인코딩이 장치와 동일. 송출 선택은 펌웨어의 `moqt_wire_pick`(§5.1.2), 창 식과 속도 추정기(estimator 2)도
  펌웨어에서 이식.
- 객체는 전체 도착 후 전달(store-and-forward), 헤더의 우선순위·그룹·서브그룹·속성 그대로. 페이로드는 읽지 않음.
  릴레이 체류 중앙값 11 µs(로컬 시험).
- 캐시: 결과 전부 + 최근 이미지 64개. 새 하류 세션은 시작 시 캐시를 채워 받아 늦은 참여·재연결 FETCH에 응답.
- 하류 keep-alive 1 s(유휴 세션 유지), alert 정책은 결과 미확인 동안 50 ms 탐침.
- `relay_receiver.py`: remote_ota_trial의 수신기 자리에 들어가는 래퍼. 릴레이·netns·구독자(receiver_draft21.py --connect) 실행,
  첫 홉 events.jsonl 생성, 단절 일정 적용, links.json 기록, 종료 시 netns 정리.
- `analyze_relay.py`: 구독자마다 `<run>/an-<name>`을 만들어 analyze_evidence_utility로 경보 지연·E 계산, 구독자 링크 단절로 분리, 홉 분해.
- `tools/campaign_relay.sh`: 장치 이미지 ao/aq(같은 빌드, 이름만 달라 해시가 다름)를 번갈아 써서 매 회차 OTA로 재시작.
- 이미지 타임아웃(prio-to, alert)은 이미지 마감 D = 10 s.

## 독립변수: 릴레이 송출 정책 (Q1)
| 이름 | 규칙 | 의미 |
|---|---|---|
| R-fifo | 도착 순서대로 송출, 우선순위 무시 | 페이로드·헤더를 해석하지 않는 단순 릴레이 |
| R-prio | draft-21 §5.1.2 순서(구독자 우선순위 → 퍼블리셔 우선순위 → 그룹 순서) | 표준이 요구하는 최소 동작 |
| R-prio-to | R-prio + 이미지 트랙 전달 타임아웃(§5.2, 장치가 준 값) | 표준 요소만 사용 |
| R-alert | R-prio-to + 구독자별 이미지 창(망 내 이미지 바이트 ≤ 예산×추정 속도) + 결과 탐침 | 제안 규칙을 릴레이 송출에 적용 |

장치는 고정: mus-alert-probe (al-v4 결과 확인 후. 탐침 효과가 없으면 mus-alert).
R-alert의 창은 장치 펌웨어와 같은 식을 쓰되 aioquic의 혼잡 윈도·bytes_in_flight로 추정.

## 실험
| 단계 | 내용 | 회차 | 시간 |
|---|---|---|---|
| RL-0 | 구현 검증: 장치 → 릴레이 → 구독자 1, 셰이핑 없음. 직결 대비 경보 지연 차이 = 릴레이 체류 시간(목표 p95 < 2 ms) | 3 | 15분 |
| RL-1 (Q1) | 정책 4종 × 3구독자 동시(128k/512k/trace) × 5라운드. 한 회차에서 3링크가 동시에 측정됨 | 20 | 약 1.2시간 |
| RL-2 (Q2) | 이질 구독자: sub1 경보만, sub2 경보+이미지, sub3 기록. 정책 R-alert, 5라운드. 대조: 직결 1구독자(al-v4)와 장치 업링크 바이트·첫 홉 경보 지연 비교 | 5 | 20분 |
| RL-3 (Q3) | sub3를 5/15/30 s 끊었다 재연결(회차당 3회) → joining FETCH로 빠진 경보 복구. 대조: 캐시 끈 릴레이(FETCH를 장치로 전달). 늦은 참여(회차 중간에 sub 추가) 포함 | 2조건 × 5 = 10 | 40분 |

모두 낮(카운트 정상 조건)에만, 기존 dark-burst 가드 유지. 회차 120 s.

## 측정 지표
- 구독자별 경보 지연(생산→구독자 도착) p50/p95/100 ms 초과 비율, 회차 단위 부트스트랩 95% 구간. 링크 정상/단절 후 분리(기존 정의).
- 홉별 분해: 첫 홉, 릴레이 체류, 둘째 홉.
- 유실: 구독자별 경보 완전성(장치가 낸 경보 대비 수신, FETCH 복구 포함).
- 복구: 재연결→마지막 빠진 경보 도착 시간, FETCH 요청 수, 장치 업링크 추가 바이트(캐시 있음 0이어야 함).
- 이미지 품질 E: 구독자별.
- 장치 업링크 바이트: 구독자 수와 무관해야 함.

## 예상 결과와 논문에서의 위치
- R-fifo, R-prio: 128k 구독자에서 경보가 이미지 바이트 뒤에 줄 선다(첫 홉에서 본 현상이 둘째 홉에서 재현).
  R-prio-to는 타임아웃만큼 꼬리를 자른다. R-alert만 예산 안 → **같은 규칙이 장치와 릴레이 양쪽에서 성립**.
- 이질 구독자: 128k 제어기의 경보 지연이 512k 품질 화면의 이미지 양과 무관 → 트랙 구독과 릴레이 팬아웃의 이점.
- FETCH 복구: 캐시 릴레이는 장치 업링크 0바이트로 100% 복구, 캐시 없음은 장치 보유 한도(결과 슬롯) 밖의 경보를 잃는다.

원고 재구성: 기여 1 = 경보 우선 규칙의 MOQT 매핑(헤더만으로 표현, 릴레이가 집행), 기여 2 = 홉 단위 송출 규칙(이미지 창 +
탐침)을 장치와 릴레이에 적용, 기여 3 = 캐시 FETCH 복구. al-v3/v4는 "첫 홉" 절로 이동. 관련연구는 MOQT 문헌 중심,
QUIC 손실 복구는 RFC 9002·RFC 8985 한 문단.

## 위험
- Python 릴레이 체류 지연·처리량: 512k×3 구독자는 충분하나 RL-0에서 확인. 부족하면 송출 루프만 최적화.
- aioquic 혼잡 제어(Reno)와 장치(ngtcp2 CUBIC) 차이: 창 추정 방식은 동일 식, 혼잡 제어 차이는 한계에 명시.
- draft-21 FETCH/joining FETCH 세부: 수신자 쪽은 이미 구현됨(receiver_draft21). 릴레이 쪽 응답 구현이 신규.
- 단일 장치·단일 호스트: 릴레이가 같은 호스트라 실제 망 위치는 아님. 둘째 홉은 에뮬레이션임을 명시.
